# Flight Search API (FastAPI backend)

Rebuild of the original Flask app: FastAPI + SQLAlchemy + Alembic + Postgres,
in a layered architecture (routers → services → repositories).

## Why this structure

| Old (Flask)                                   | New (FastAPI)                                    | Why |
|------------------------------------------------|---------------------------------------------------|-----|
| Blueprint route does SQL directly              | `routers/` → `services/` → `repositories/`        | Each layer has one job: HTTP parsing, business rules, or data access. You can unit-test business logic without a real DB, and change storage without touching business rules. |
| Server-side session (`session['username']`)    | JWT (`core/security.py`, `deps.py`)               | Stateless - no server-side session store needed, works naturally with a separate frontend origin. |
| Raw SQL strings with `%s` placeholders          | SQLAlchemy models (`models/`) + ORM queries        | Type-safe queries, autogenerated migrations, no manual string-building. |
| No validation - `request.form['x']` can KeyError | Pydantic schemas (`schemas/`)                     | Bad requests are rejected with a clear 422 error before your code even runs. |
| Manually written HTML forms                     | Auto-generated docs at `/docs`                     | FastAPI reads the Pydantic schemas and route signatures to build interactive Swagger docs for free. |
| `.SQL` file you run by hand                      | Alembic migrations (`alembic/versions/`)            | Versioned, reproducible schema changes - `alembic upgrade head` gets anyone to the same state. |

## Directory guide

```
app/
  core/         # config (env vars) + security (password hashing, JWT)
  db/           # SQLAlchemy engine/session setup
  models/       # one file per DB table (SQLAlchemy ORM classes)
  schemas/      # one file per domain (Pydantic request/response models)
  repositories/ # raw DB queries only - no business logic
  services/     # business rules (dynamic pricing, 24h cancellation, auth) - call repositories
  routers/      # HTTP endpoints - call services, never repositories directly
  deps.py       # shared FastAPI dependencies (DB session, JWT auth)
  main.py       # app entrypoint, wires routers together
alembic/        # migration scripts
tests/          # pytest suite - conftest.py has the fixtures, factories.py builds test data
```

Read them in this order to understand a feature end to end, e.g. booking:
`routers/bookings.py` → `services/booking_service.py` → `repositories/booking_repo.py` → `models/booking.py`

## Running locally

```bash
# 1. Postgres (via Docker)
docker run -d --name flight_search_postgres \
  -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=flights \
  -p 5432:5432 postgres:16

# 2. Python deps
pip install -r requirements.txt

# 3. Apply migrations (creates all tables)
alembic upgrade head

# 4. Run the dev server
uvicorn app.main:app --reload --port 8000
```

Then open **http://127.0.0.1:8000/docs** for interactive API docs, or
**http://127.0.0.1:8000/health** for a liveness check.

## Making a schema change

1. Edit/add a model in `app/models/`.
2. `alembic revision --autogenerate -m "describe the change"` - Alembic diffs your models against the live DB and writes a migration script.
3. Review the generated file in `alembic/versions/` (autogenerate isn't perfect - check it).
4. `alembic upgrade head` to apply it.

## Tests

```bash
# one-time: create a separate test database
docker exec flight_search_postgres psql -U postgres -c "CREATE DATABASE flights_test;"

pytest -v
```

Tests hit a real Postgres database (`flights_test`), not mocks - each test gets
a clean slate because `tests/conftest.py` truncates every table after each test.
`tests/factories.py` has helpers for seeding a customer/staff/flight quickly.

## Business rules worth knowing (carried over from the original app)

- **Dynamic pricing**: once a flight is ≥60% booked, the price jumps 20% above base price (`services/booking_service.py::CAPACITY_SURCHARGE_THRESHOLD`).
- **Cancellation window**: tickets can't be cancelled within 24 hours of departure (`services/booking_service.py::cancel`).
- **Reviews**: a customer can only review a flight they've actually flown on (departure in the past + a purchased ticket), and only once.

## A real bug worth knowing about: always give routes a `response_model`

`ReviewService.staff_summary` (used by the staff ratings dashboard) originally returned a plain
dict wrapping whatever the repository gave back - including `average_ratings_for_airline`'s
result, which is a list of raw SQLAlchemy `Row` tuples (from a `query(col1, col2, col3)` of
individual columns, not a full ORM model). FastAPI's `jsonable_encoder` can serialize an ORM
model instance via `vars()`, but it has no idea what to do with a bare `Row` - the endpoint
500'd. Two lessons that generalize beyond this one bug:

1. **Every route should declare a `response_model`**, even when the return value "just happens"
   to serialize correctly without one - that's what caught the other staff routes that had the
   same latent risk (`routers/flights.py`'s staff routes, `routers/staff_admin.py`) before they
   became real bugs, not after.
2. Anywhere a repository method returns `query(col1, col2, ...)` instead of `query(Model)`, the
   service layer must convert each row into a real object (a Pydantic schema, here) before it
   reaches a router - see `AverageRatingOut` in `schemas/review.py` and the conversion in
   `ReviewService.staff_summary`.

This is now pinned by a regression test (`tests/test_reviews.py::test_staff_summary_returns_average_ratings_and_reviews`).
